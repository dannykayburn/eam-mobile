Design notes — what changed vs. base
01
Left icon rail + searchable tree, not a top menu bar
Base ships both flavours; the left one was asked for. The tree is searchable because a menu whose deepest item is Additional Features ▸ WO Screens ▸ Customer Quotes can't be driven by hover-cascade at speed.
Menu Structure.png
02
The list / split / record tri-toggle is gone
That control made the user run a window manager. Now: double-clicking a row opens the record with its tabs, and the list it came from stays as a context rail you can collapse from its own header chevron, drag to resize, or reopen from the carrot strip it leaves behind — the control lives on the thing it affects, so there's no layout-mode button in the record header at all. Moving between records is a prev/next stepper, which is where that intent actually lives. Single click just marks a row, keeping it free to mean "this is the row I'm talking about"; ↑↓ then Enter is the keyboard equivalent.
red-marked in List View.png
03
14 toolbar glyphs → Save + a grouped overflow
This is the mobile app's own locked rule (§8.4) applied to desktop: row-scoped actions live on the row; everything else is a header action in the overflow. Base's toolbar is the exact anti-pattern that rule exists to prevent.
design-decisions-v3-1 §8.4
04
Insert is its own surface, not a second mode
Base launches one screen in two modes. Create is now a right-hand panel carrying only what a new record needs — modelled on the app's Insert Mode (§9.6) — which then hands off into the full record view.
design-decisions-v3-1 §9.6
05
A static, grid-driven header the rest arranges around
The reference screen puts header info in the first collapsible section, which means the fields that say what the record even is can be collapsed away — and several of them turn up again lower down. Here it splits in two. The banner owns identity (beefy mono code + inline-editable description, in the app's own style), the progress capsule, the status control and the hours block — all read-or-derived, which is why it can collapse on scroll without costing anything. Progress is segmented, one per checklist item, using the rail's own .seg tiering (done / next / future) rather than a sliding fill — a single bar would have been a fourth way of saying "progress" that the app doesn't have. Every number in the banner is derived from the live collections, so ticking an item moves it. The header section below is non-collapsible, unlabelled (the banner already named the record) and holds only what classifies the record — driven by HEADER_COLS, three balanced columns of three: Type/Priority/Criticality, the Equipment/Location/Department stack, and Organization/Safety/Warranty. Type leads, and carries the WO Type badge in its solid-fill form (§23.3) just as the app's Type field does. None of those nine appears anywhere else on the record.
dark reference screenshot
06
One field system, 14 canonical types
Every field comes from one fld() factory carrying the app's own 14 field types (§5.2), in the two containers the app already has: Grid (label notched on the box's border) for the header, List (label left, value right) for the narrow cards. Type is now legible at a glance — identifiers mono, numerics tabular and right-aligned, LOVs a description-over-code stack (the app's order; the first pass had it inverted), protected fields with a lock and no border, real focus rings, and affordance cues that resolve on hover. Clicking anywhere in a field invokes its editor, not just the corner glyph.
was: one generic bordered box for everything
07
Collections are list-detail containers, not flat fields
Activities, Checklist, Book Labor and Parts run through one engine. Rows scroll inside their own container, a row opens in place into full fields, Plus inserts without leaving the record, and a quick-filter bar sits above every list. Base shows activity #1 as a flat block of fields and banishes the rest to another tab; this is the paradigm that breaks. On the record view the container sits in a card, on a child tab it's full-bleed — same engine.
the app's List/Detail model, in a container
08
Closable tabs aren't closable any more
A tab you can close is another piece of window management. Tabs carry counts and a red dot when they hold something required and unmet — Closing shows one until its comments are written.
09
Required markers came back — knowingly
The app removed them app-wide (§23) because a required field's edit popup already blocks Clear, so the marker warned about an unreachable state. Desktop has no such popup and a genuinely blank form exists, so the rationale doesn't transfer. Same logic that makes Insert Mode the app's one documented exception (§9.8).
divergence from app
10
Child tabs are one shell, nine times
Every tab other than Record View and Closing is a layout illustration with toast stubs — there to show how a child tab is laid out and navigated, not to work. They all share one shell (toolbar → grid or list → footer totals) so the pattern is visibly one pattern. Rows open in place with their row-scoped buttons — the app's Action Row (§17.4/§18.3) — rather than navigating away.
stubs, not features
11
Shared with the app, not re-derived
Colour tokens, Inter/JetBrains Mono, the WO Type colour+icon badge (§23.3), Status pill tiers (§15.4 — green for Released only), mono-for-identifiers, the outlined Organization badge (§23.5), Comments' top-3-plus-View-more (§7.2), and Closing's sequential code unlock (§19.3) are all the app's, copied verbatim.
12
Protected fields stopped shouting
Base draws read-only data as heavy bordered grey boxes, which makes the least actionable thing on screen the loudest. Here protected is a flat fill with no border; editable keeps the border.
