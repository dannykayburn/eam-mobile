Findings — Grid vs. List consolidation (2026-07-23). Confirms what's already consistent, flags real exceptions, and calls out open questions this file is the first to surface — nothing below is locked into design-decisions-v3-1.md yet pending your review.
Notes / Description — locked, this session. Always double-wide. In Grid that's a real rule (.attr-item.full-width, forced regardless of position — placed first here so it never depends on landing on an odd count). In List it's a no-op, since every List row is already full-width — the rule only has visible teeth in Grid.
Badge / Icon LOV — decided, 2026-07-23; rebuilt 2026-07-24, real bug found on a real device. Allowed in a List row, icon leading (left of the description), grouped with it at the right edge of the row. The first build wrapped {badge, value} in their own nested flex div (justify-content:flex-end) — on a real device the badge rendered detached near the label instead of grouped with the value. Rebuilt using the same proven margin-left:auto trick .field-checkbox already uses elsewhere: the badge is now a plain sibling of .field-value, no wrapper div, one flex context instead of two. Grid: unchanged, already the real Type/Priority pattern.
LOV — Code Only — replaces "LOV — Description Only" entirely, 2026-07-24 (real design reversal, not just this file). Design-decisions-v3-1.md §5.2 locked "Grid's plain-LOV items show description only, no code" on 2026-07-16, reasoning that Grid LOVs are reference-data lookups being surfaced prominently, not identifiers. That's now reversed by direct user decision: codes ARE wanted in Grid fields, so there is no "description only" LOV type at all — a plain Grid LOV either shows a code (this type) or the badge/stacked code+description types above. Mono in both containers, but the SIZE now deliberately diverges between them (both same day): Grid — 14px looked visually short next to its row-mates (the 28px badge icon, and Code + Description's own 2-line stack) — .attr-text.mono is font-size 24px, line-height exactly 1, as its standard, documented size, not a one-off tweak on this one example. List — a deliberate exception, standard 14px value size, still mono font-family only (.field-value.mono) — List's own row-mates (a plain chevron, a 2-line stack) don't create the same "looks short" mismatch the 28px Grid badge did, so it doesn't inherit Grid's size bump. Real screens not yet updated: WO Record View's own Department field (the Header Fields grid's original description-only example, §5.2) still shows description-only — flagged, not touched this pass, since this file's scope was the field-TYPE comparison, not a sweep of every real screen using the old rule.
LOV — Code + Description / Identifier — decided, 2026-07-23. Same field type going forward ("code + description," no separate "Identifier" name) — kept as 2 examples here only because the naming consolidation doesn't retroactively change which is which yet. Stacked is the standard shape in both containers. Stack order: Grid locks to description-over-code (the two examples above now render this way — was code-over-description in the first pass, flipped after a brief side-by-side comparison, now removed). List is unchanged — its pre-existing .field-lov-value stays code-over-description, since this decision was scoped to Grid LOVs specifically, not applied app-wide.
Inline Text / Notes — decided, 2026-07-23; a 2nd, more serious real bug found and fixed 2026-07-24 on an actual device. Tapping anywhere in the row (not just the textarea itself) always lands the cursor at the end of the existing text, matching the header description field's own already-proven pattern (onDescTap()) — focusInlineField() in eam-shared.js, replacing the old this.querySelector('textarea').focus() onclick everywhere it appeared (6 real screens plus the shared fieldRowInline() template). Wrapping/height bug: long values were visibly cutting off instead of growing the row taller — root cause was a flexbox gotcha, not a missing autoGrow() call: .field-inline-input's base flex:1 sets flex-basis:0%, which governs the MAIN axis size; inside a column-direction parent (List's .stacked, Grid's .attr-item) the main axis is vertical, so flex-basis:0 controlled HEIGHT — and because the same rule also sets overflow:hidden, the browser's automatic content-based minimum-size safety net was suppressed, letting the box collapse toward 0 regardless of autoGrow()'s own explicit inline height. Fixed with flex:none on both the List and Grid override rules (eam-shared.css) — never caught before because no existing real screen's inline-text field had ever been tested with genuinely long, multi-line-wrapping content.
Currency / Number / Date / Date/Time — consistent, no exception. All four are identical in Grid and List — same sheets, same formatting, same required left-bar recipe (.attr-item.required::before already mirrors .form-field.required exactly, confirmed live above on the two required examples).
Time Only — reversed, 2026-07-24: right-aligned everywhere, no exceptions in the CSS; confirmed as a real iOS platform limitation, not chasing it further. The 2026-07-23 pass added a Grid-only left-align override (.attr-value .time-input{text-align:left}) — removed entirely; both containers now inherit the identical base .time-input{text-align:right} rule, uniformly, no exceptions in the actual CSS. On a real iOS device, the rendered result still doesn't match that rule in either container: Grid shows the native control centered, List shows it left-aligned — despite both now resolving to the exact same text-align:right at the CSS level, confirmed on desktop (right-aligned correctly there, this is not a CSS authoring mistake). This is a known WebKit/iOS limitation, not fixable from page CSS: <input type="time"> renders as a fully native OS control on iOS Safari, and its internal segment layout doesn't reliably honor text-align at all — same category as the already-documented 24-hour/lang="en-GB" quirk on this exact control. Accepted as-is; no further CSS attempts planned, since none can reach inside a native-rendered control's own layout.
Checkbox — decided, 2026-07-24, after comparing 7 options live on a real device. Superseded both the original (2026-07-23) centered-in-value-row treatment and this file's earlier "fully consistent, no change needed" framing — the user asked to see more of the design space first (grid-checkbox-size-alignment-options.html: 4 variants of the stacked shape at 2 sizes/2 alignments, 3 variants of a dedicated-right-zone row shape) and picked option 6: single row, label left, a fixed ~28%-wide zone on the right holding a medium (24px) checkbox — new .attr-item.checkbox-zone-row/.attr-checkbox-zone in eam-shared.css, replacing the old centering rule entirely. Applied to the one real consumer too (WO Record View's Activity Edit popup, Completed checkbox) — toggleCheckbox() needed no changes, same as before.
Protected — decided, 2026-07-23, approved with one change from the first pass. .attr-item.protected is good; the lock icon moved onto the label's own row (.attr-label-row, new) instead of sitting next to the value below it — List's single-row .form-field.protected already put the lock "in the same row as the label" trivially (it's one row total), Grid's 2-row column layout didn't until this change. Ready to promote to eam-shared.css.
Long-text — decided, 2026-07-23: locked explicit, not left to coincidence; a real carriage-return bug found and fixed 2026-07-24. .attr-item.full-width is applied directly regardless of position, matching Notes/Description's own rule — not relying on the "odd item spans the row" fallback the original 13-field count happened to trigger. Carriage-return bug: Long-text's full-screen editor already supported Enter-key line breaks (nothing ever blocked it), and the underlying value already stored them (saveTextEditor() just assigns the raw string to textContent) — but the COLLAPSED display span never rendered them: default white-space:normal collapses \n to a plain space like any other whitespace run, so a multi-line value read as one run-on line. New .multiline modifier (white-space:pre-wrap, plus left-align on .field-value since a right-aligned paragraph reads badly) fixes both containers here and the canonical sample-screen-standard-model-prototype.html's own Long Note field, the only other real single-field Long-text consumer.
Cross-cutting note: a real pre-existing bug, not part of this comparison. The Time Only example above intentionally omits an onchange handler — the canonical sample-screen-standard-model-prototype.html's own Start Time field calls setFieldValue(this,this.value), a function that doesn't exist anywhere in this app (also referenced, equally broken, in Book Labor). Harmless today (the native input still displays its own value), but flagged here rather than silently copied into a 3rd file.
