Form factors — phone portrait vs tablet landscape

Low-fidelity. Grey boxes and real pixel numbers, so the argument is about layout and not styling. Rev 2 — retargeted from "rotated phone" to tablet, which changes the problem completely.

Scope — mobile app only

Form-factor and landscape adaptation is unique to the mobile app and the screens under it. The Workflow Designer Portal is a web surface: a browser window is already arbitrarily sized and the portal already behaves like a desktop web app, so it needs no distinct modes. This is the exact mirror of §30.7's "OCTAVE SCOPE: base screens only" — that rule keeps the base design system out of the app; this one keeps the app's form-factor work out of the base portal. Neither crosses the seam.

02The organising idea — §4.2's own three levels

This does not need a new model. §4.2 already states one, in its opening sentence: the nav bar is "persistent global chrome, distinct from the per-record tab rail (§7.1) and the WO workflow's step rail (§14.2), which both operate one level down, inside a single record."

Band 1 · app — Home / Work / Notifications, avatar, sync§4.2
Band 2 · record — step rail or tab rail§14.2 / §7.1
Band 3 · content — the screen itself§5.2

A phone in portrait can only show one level at a time — which is precisely why the rails collapse into tappable pills and why the bottom nav hides the moment a record opens. Those are compromises forced by 393px, not preferences. A tablet can show all three at once, as vertical bands. The tablet layout is therefore an expression of the existing model rather than a new one.

The band rule: at most three bands, and the list pane and the record rail never coexist. Browse = nav rail + list + detail. Execute = nav rail + record rail + content. Four bands — nav rail, list, record rail, content — is the failure mode, and it is what naive "just add a pane" produces.

03Phone landscape — the degenerate case, contained

Dealt with briefly so it is not a hole. At 349px of height with ~200px of fixed chrome there is no good layout, and a tablet-style two-pane makes it worse by adding a band.

OptionVerdict
Keep the centred 430px column Recommended. What happens today, by accident, via .app{max-width:430px}. It is coherent, nothing is broken, and it costs nothing to keep. A rotated phone is an incidental state, not a work posture.
Full tablet treatment No. Adds a band to the axis that has none to give.
Lock to portrait No. Ruled out by Apple's HIG, and it would also block the tablet, which is the actual target.

So the breakpoint keys on width, not orientation: @media (min-width:840px) and (min-height:600px) — Material's expanded width class plus a real height floor. A rotated phone (349px tall) fails the height test and keeps the phone layout. A tablet in portrait (820×1180) fails the width test and also keeps the phone layout, correctly — tablet portrait is a big phone, and that is fine.

This breaks §30.16, and it is the one place the tablet forces a real authoring change. HOME_FOLD = 3 is arithmetic on a 390px device (390 − 28 padding, 100px tiles, 10px gaps), and the rule it protects is "line one is what the technician sees without swiping". On a tablet the same arithmetic over 1102px gives a fold of 9. The Home editor draws exactly one fold, so it cannot currently be truthful for both.

Proposed resolution: author to the phone fold; the tablet is a superset. The editor keeps drawing the 3-tile fold as the guarantee, because what fits a phone fits a tablet — never the reverse. The tablet then simply reveals more of row one without swiping, which can only ever be a bonus. That keeps one fold in the editor, one authored layout, and no per-device variants — see flag 2 in section 08.

This breaks §4.2, and it cannot be styled around. §4.2 says the bottom nav is "visible while browsing; hidden entirely the moment any record is open" — a binary, browsing XOR record-open. The frame above has a list and an open record showing at the same time, so both are true. Proposed resolution: on tablet the two stop being exclusive. The hide-on-record-open rule stays exactly as written for phone portrait, where it is a space compromise. See flag 1.
Browse vs execute — where the detail pane stops. The detail pane shows the record and its header actions. Starting a workflow promotes to full width (section 06), dropping the list pane so band 2 can be the step rail. A workflow step is a deliberately focused, one-thing-at-a-time surface (§14) and squeezing it beside a list would both crowd it and produce the forbidden fourth band. So: browse = two-pane, execute = full-width.

08What this costs — the decisions you need to make

Two locked rules genuinely have to change, and you have already authorised proposing against them. Both are narrow, and both keep phone portrait exactly as written.

1. §4.2's browsing XOR record-open binaryamendment required

"Visible while browsing; hidden entirely the moment any record is open." Two-pane list-detail makes both states true simultaneously, so this is a model change, not a styling one. Proposed: the exclusivity is a phone-portrait space compromise; on tablet band 1 persists always and the record nests in bands 2–3. §4.2's three-item membership (Home, Work, Notifications — Equipment deliberately excluded) is unchanged; only the visibility rule gains a form-factor scope.

2. §30.16's HOME_FOLD is single-valuedamendment required

HOME_FOLD = 3 is arithmetic on 390px; the tablet's is ~9, and the Home editor draws one fold. Proposed: author to the phone fold and treat the tablet as a superset — the editor keeps drawing 3 as the guarantee, since what fits a phone fits a tablet and never the reverse. One fold, one authored layout, no per-device variants. This touches the portal's Home Layouts area, which is otherwise out of scope — it is a rule change, not a portal layout change.

3. §8.4's button placement survives untouchedno change

§8.4 is semantic — row-scoped → Action Row, everything else → header ellipsis. The tablet keeps the horizontal action bar at the foot of band 3, so nothing moves at all. Worth stating because rev 1 proposed standing it up and that would have needed checking.

4. §5.2 containers survive untouchedno change

Band 3 at ~700–900px is wide enough that authored 2-up Grid containers read correctly without re-columning. The rule stands: form factor never changes an authored container's column count, since §5.2 makes shape a per-container authoring property. It should be enforced at the setter the way "a Grid cannot be Collapsed" already is.

5. The fourth band on child tabsneeds a device

Section 07 bends the band rule. Flip it on a real tablet and choose: keep the four narrow bands, or collapse the equipment list to a chooser as on the phone. This is the same shape as the existing chooser/split open item, so it can reuse that dev toggle.

6. Rotation and pane stateneeds a decision

Two-pane introduces a selected row, which does not exist in portrait. Rotating into landscape has to choose a selection (first row? none, with an empty detail pane?) and rotating out has to discard one. "Empty detail pane with a prompt" is the conventional answer and the honest one. Not a default — a call.

7. Safe-area insetsprerequisite

Only safe-area-inset-bottom is used anywhere in eam-shared.css. A full-width layout needs left/right. Smaller on a tablet than a notched phone, but still a real gap and a prerequisite rather than a follow-up.

8. Is this an R-level requirement?scope

Tablet support is not in the design doc's requirements. If it is real it belongs there as a requirement, with the band model as a locked spec rule — not as a per-prototype fix. That sequencing question is worth settling before any code, because it decides whether the 16 screens get touched once or sixteen times.
